§11.1 动机:摊还 vs 平均 vs 最坏

11.1.1 三种"平均"不是一回事

前几章我们反复说"list 尾部插入平均 O(1)、最坏 O(n)"。这个"平均"是什么意思?复杂度分析里有三种不同的说法,极易混为一谈:

说法对什么取平均需要什么假设例子
最坏情形不取平均,取最差输入无假设,对所有输入成立快排最坏 O(n2)
平均情形对输入的概率分布取平均必须假设输入分布(如"等可能")快排平均 O(n log n)
摊还对操作序列取平均无概率假设,对任何序列成立n 次 list.append 总代价 O(n)

摊还分析:数据结构上任意一个由 n 个操作组成的序列,若总代价为 O(n·f(n)),就说每个操作摊还代价为 O(f(n))。它不假设任何概率分布,对最恶劣的序列也成立。

11.1.2 为什么需要摊还分析

回头看前几章,至少有三个结论是"背下来"而没证明的:

  • 第 3 章:list 倍增扩容使 append "平均 O(1)"——没证明,也没说清是摊还;
  • 第 6 章:buildHeap 是 O(n)——逐个 insert 明明 O(n log n),整体下滤为何线性?
  • 第 6 章:斜堆 merge 摊还 O(log n)——单个 merge 最坏 O(n),教材直接给结论;

三个结论分别对应本章的三种方法:聚集证 buildHeap,会计证动态数组,势能证斜堆——学完本章,"背诵"变"推导"。摊还分析是算法设计的"定价"工具:一次操作贵没关系,整个序列便宜就行。

误区 1:把摊还 O(1) 当单次 O(1)

摊还 O(1) 的意思是"n 次操作总代价 O(n)",不保证单次操作是 O(1)。list 那次触发扩容的 append,单次代价仍是 O(n)——只是被前面的便宜 append 平摊了。同理,"斜堆 merge 摊还 O(log n)"不代表某一次 merge 不会花 O(n)。实时系统里单次延迟上限有时更关键,这时需要第 12 章平衡树那种"每次最坏 O(log n)"的结构。

11.1.3 摊还代价的定义

设操作序列共 n 个操作,第 i 个操作的实际代价记为 ci,总代价 T(n) = Σi=1n ci。若对任意长度为 n 的合法序列都有 T(n) = O(n·f(n)),则称每个操作的摊还代价为 O(f(n))。三种方法回答同一问题——"怎么证 T(n) 的上界"——只是记账方式不同:

方法一句话数学工具
聚集分析先算总账,再平均Σ 求和
会计方法每个操作预存,贵的取款账户余额非负
势能方法把"存款"记在数据结构状态上势能函数 Φ 的差
记号说明

本章公式密集,记号统一:ci 第 i 个操作的实际代价,ai 其摊还代价;Φ(Di) 第 i 个操作结束后结构的势能(读"Phi"),ΔΦ = Φ(Di) − Φ(Di−1)。

§11.2 聚集分析:栈操作序列

11.2.1 方法:先求和,再平均

聚集分析最直接:把 n 个操作的实际代价全部加起来得总代价 T(n),除以 n 即摊还代价。难点只在"证总代价上界"——通常靠巧妙的计数观察,而非逐个求和。

11.2.2 经典例子:栈的 push/pop/multiPop

考虑一个从空栈开始的栈,三个操作:push(代价 1)、pop(代价 1)、multiPop(k)(连续弹出 k 个元素,不够时弹到空,代价 = 实际弹出个数,最坏 O(n))。问:任意 n 个操作,总代价是多少?

直接求和会卡住:某次 multiPop 单次就花 O(n),但序列里不可能全是 multiPop——弹出的元素必须先被 push 进去,而 n 个操作最多 push n 次。关键观察:每个元素至多入栈一次、至多出栈一次,于是:

出栈总次数 ≤ 入栈总次数 ≤ n,总代价 ≤ 2n,摊还代价 O(1)。证明没做任何输入假设:任何长度为 n 的序列总代价都 ≤ 2n。若问"全是 multiPop 怎么办?"——这种序列根本不存在:栈空了就没得弹,这个"不可能"正是证明核心。

11.2.3 代码验证:总代价 ≤ 2n

示例 11-1 统计栈操作序列的实际总代价
# 模拟 push/pop/multiPop 序列,统计总代价,验证摊还结论
def multiPop(st, k):
    cost = 0
    while st and cost < k:
        st.pop()
        cost += 1
    return cost

n = 10000
st, total = [], 0
for i in range(n):
    st.append(i)                    # push:代价 1
    total += 1
    if i % 1000 == 999:             # 每 1000 次 push 来一个大 multiPop
        total += multiPop(st, n)    # 弹空:每个元素只出栈一次
print(f"操作数 n = {n}, 总代价 = {total} (≤ 2n = {2*n}), 摊还 = {total/n}")
# 输出:操作数 n = 10000, 总代价 = 20000 (≤ 2n = 20000), 摊还 = 2.0

§11.3 会计方法:动态数组的"存 3 元"证明

11.3.1 方法:预存存款

会计方法把摊还代价看作"收费":每个操作收摊还代价 ai 元,其中 ci 元支付该操作本身,ai − ci 元存入账户,留给未来昂贵操作取用。唯一要求是:

任何时刻账户余额非负:对每个前缀 Σi=1k (ai − ci) ≥ 0。

余额非负 ⇒ 累加得 Σi=1n ai ≥ Σi=1n ci,总摊还代价是总实际代价的上界。故每个操作收费 O(1) ⇒ 总实际代价 O(n)。

11.3.2 动态数组:插入收 3 元

回到第 3 章的动态数组:append 平时只写一个元素(实际代价 1);容量满时倍增扩容要拷贝全部旧元素(实际代价 O(n))。CPython 的 list 也是同一机制——扩容搬的是对象指针,代价照旧按"拷了几个元素"算。定价 3 元:

  • 1 元:支付本次写入;
  • 2 元:存入账户,留给"未来某次扩容时本元素的拷贝";

扩容时每拷贝一个旧元素从账户支付 1 元。直觉:设扩容前容量为 m(已满),拷贝费 m 元;这 m 个元素中后 m/2 个是上次扩容后才插入的,每个带 2 元存款,合计恰好 m 元;前 m/2 个"老元素"的存款原封留存。归纳下去,账户永不为负。

11.3.3 存款非负的 Σ 推导

严格版本用总账。设元素个数 s、容量 c = 2k,累计扩容拷贝费是等比级数:Σj=0k−1 2j = c − 1。总收费 3s,总花费 s(写入)+ (c − 1)(拷贝),余额 = 3s − s − (c − 1) = 2s − c + 1。数组满才扩容,刚扩完 s = c/2,故 s ≥ c/2,余额 ≥ 1 > 0。余额恒正 ⇒ 总摊还 ≥ 总实际 ⇒ 总代价 ≤ 3n,摊还 O(1)。证明只需"容量按常数因子增长",1.5 倍、1.125 倍都行;唯独"每次 +1"不行(摊还 O(n))。

C 的 realloc 手动扩容Python 的 list.append
realloc 扩容,size 变化自己记账append 自动扩容,内部维护 size/capacity,可用 sys.getsizeof 观察
扩容策略自己写,每次 +1 就退化成 O(n2)倍增(约 1.125 倍)内建,摊还 O(1) 由 CPython 保证
失败返回 NULL,旧指针要自己处理分配失败抛 MemoryError,旧对象不受影响
扩容后旧指针全部失效list 存对象指针,扩容只搬指针,已有引用仍有效

11.3.4 代码验证:账户余额永不为负

示例 11-2 会计方法视角的"存 3 元"动态数组
# 每次 push 收 3 元(1 元自用 + 2 元存款),扩容拷贝从账户支付。
class BankArray:
    def __init__(self):
        self._buf = [None] * 1
        self._size = 0
        self._cap = 1
        self.balance = 0                # 账户余额
        self.min_balance = float("inf") # 全程最低余额
    def push_back(self, x):
        self.balance += 3               # 收 3 元
        self.balance -= 1               # 支付本次写入
        if self._size == self._cap:     # 容量满:倍增
            new_buf = [None] * (self._cap * 2)
            for i in range(self._size):
                new_buf[i] = self._buf[i]
                self.balance -= 1       # 每拷 1 个付 1 元
            self._buf = new_buf
            self._cap *= 2
        self._buf[self._size] = x
        self._size += 1
        if self.balance < self.min_balance:
            self.min_balance = self.balance

§11.4 势能方法:势能函数与通用框架

11.4.1 方法:势能函数 Φ

势能方法把会计方法的"账户"从具体元素上抽象出来,记在数据结构的状态上。定义势能函数 Φ(D) 为状态 D 的一个数值属性(如"栈中元素个数");设 Di 为第 i 个操作结束后的状态,D0 为初始状态,则第 i 个操作的摊还代价定义为:

ai = ci + Φ(Di) − Φ(Di−1),即 摊还代价 = 实际代价 + 势能变化 ΔΦ。

两边求和,中间项错位相消(望远镜求和):Σi=1n ai = Σi=1n ci + Φ(Dn) − Φ(D0)。

只要 Φ(D0) = 0 且 Φ(Di) ≥ 0 对所有 i 成立,就有 Σ ai ≥ Σ ci,总摊还是总实际代价的上界。与会计方法唯一区别:会计把存款绑在具体元素上,势能把它绑在整个结构的状态上——会计方法是势能方法的特例。

11.4.2 栈的例子重推

取 Φ(D) = 栈中元素个数,Φ(D0) = 0,且元素个数永不为负,条件满足。逐个操作算摊还代价:

  • push:实际 1,ΔΦ = +1,摊还 = 2;
  • pop:实际 1,ΔΦ = −1,摊还 = 0;
  • multiPop(k):弹出 k′ 个,实际 k′,ΔΦ = −k′,摊还 = 0;

总摊还 = 2 × push 次数 ≤ 2n,与聚集分析一致。"贵的"multiPop 摊还代价是 0——它消耗的正是 push 积累的势能。

误区 2:把平均情形分析当摊还分析

"快排平均 O(n log n)"与"list 插入摊还 O(1)"是两回事:前者对输入排列取平均,前提是"输入等可能",数据分布一变结论就失效;后者对操作序列取平均,对任何序列都成立——攻击者精心构造"append 到满再 append"的序列,总拷贝也 ≤ 2n。口诀:"随机""等可能""期望"是平均分析;"任意序列""总代价上界"是摊还分析。

11.4.3 自调整表(move-to-front):结论与直觉

自调整表:元素排成一列,每次访问后移到表头(move-to-front),频繁访问者越用越靠前。访问位置 k 的元素实际代价 O(k)(要挪动 k−1 个元素),但摊还代价 O(log n):n 次任意访问的总代价 O(n log n)。

证明思路(从简,见教材):取势能 Φ = 表中逆序对个数。把被访问元素从位置 k 提到表头,破坏约 k 个逆序对(势能下降),新产生的逆序对有界;势能变化与移动代价大体抵消,余项用对数界住。结论:摊还 O(log n)。自调整思想在工程中遍地开花:LRU 缓存、"最近使用的放前面"的接口设计都是亲戚。

11.4.4 势能方法的通用框架

重点:势能方法四步框架
  1. 选 Φ:只依赖数据结构的状态(元素个数、逆序对数……);
  2. 验证:Φ(D0) 有界且 Φ(Di) ≥ 0;
  3. 逐个算:ai = ci + ΔΦ,昂贵操作 ΔΦ 为负、便宜操作为正;
  4. 累加得界:Σ ai = O(n·f(n)) 则摊还 O(f(n))。

选 Φ 的直觉:Φ 应度量"结构中蕴藏的、未来必然要做的活儿"——待弹出的元素、待拷贝的元素、待"纠正"的逆序对。消耗这些"存量"时,实际代价由势能下降支付。

误区 3:势能函数选错,存款为负

Φ 必须非负,这是势能方法的前提。反例:栈取 Φ(D) = −(元素个数),Φ(D0) = 0 但 Φ(Di) < 0,此时 Σ ai < Σ ci,总摊还代价低于总实际代价,不再是上界,"总代价 O(n)"直接失效。更隐蔽的错误:选 Φ 依赖操作历史(如"Φ 取 i 的奇偶"),望远镜求和不再成立。选好 Φ 后务必检查"非负"与"只依赖状态"两条。

§11.5 摊还在堆上的应用

11.5.1 斜堆:merge 摊还 O(log n)

第 6 章讲过斜堆:没有平衡信息,merge 时无条件交换左右子堆,单次 merge 最坏 O(n),但merge 摊还 O(log n)。证明用势能法(从简):称"重"结点为右子堆大小 ≥ 左子堆一半者,势能 Φ = 重结点总数。merge 的实际代价 = 右路径步数 = 轻边数 + 重边数;轻边数 ≤ log2 n(每经一条轻边子树至少减半),每条重边由势能下降 1 支付,交换后至多产生 log n 个新重结点,两抵得 O(log n)。斜堆是"摊还换来简单"的典型:无平衡信息、代码最短。

11.5.2 二项队列:insert 摊还 O(1)

二项队列的 insert 可看作"二进制加法":二项树大小是 2 的幂,合并两个同大小树就像进位 1+1=10,于是借用二进制计数器的经典结论:从 0 加 1 共 n 次,总翻转位数 ≤ 2n,摊还 O(1)。故 insert 摊还 O(1)、最坏 O(log n);deleteMin 与 merge 摊还 O(log n)。对比二叉堆:insert 最坏就是 O(log n),不必摊还——摊还分析只在结构把贵操作推迟分摊时,才比最坏更紧。

11.5.3 二叉堆 buildHeap:聚集分析回顾

第 6 章说 buildHeap 是 O(n),现在证明。buildHeap 从第 ⌊n/2⌋ 个结点起逐个下滤,关键是把结点按高度而非按深度计数:完全二叉树中高度为 h 的结点至多有 n/2h+1 个,每个下滤 ≤ h 层,总代价:

T(n) ≤ Σh=0log n (n/2h+1)·h = (n/2)·Σh=1∞ h/2h = (n/2)·2 = O(n)。

级数 Σh=1∞ h/2h = 2。这就是"逐个 insert 是 O(n log n)、整体下滤只要 O(n)"的原因:多数结点在底层、下滤路径短;高层结点下滤深,但数量指数级地少。下面代码统计真实步数验证。

示例 11-3 统计 buildHeap 的总下滤步数(验证 ≈ n)
# 从第 n//2 个结点向前逐个下滤,统计总步数
def heapify(a):
    n, steps = len(a), 0
    def down(i):                    # 下滤一个结点
        nonlocal steps
        while True:
            l, r, m = 2 * i + 1, 2 * i + 2, i
            if l < n and a[l] > a[m]: m = l
            if r < n and a[r] > a[m]: m = r
            if m == i: break
            a[i], a[m] = a[m], a[i]
            steps += 1              # 交换一层记 1 步
            i = m
    for i in range(n // 2 - 1, -1, -1):
        down(i)
    return steps

n = 65535
a = list(range(1, n + 1))           # 升序:对最大堆最不利
s = heapify(a)
print(f"n = {n}, 总下滤步数 = {s} (理论 O(n),实测 ≈ {s * 100 // n}% n)")
# 输出:n = 65535, 总下滤步数 = 65519 (理论 O(n),实测 ≈ 99% n)

§11.6 工程印证:实测扩容拐点

11.6.1 手写倍增 vs 标准库:观察扩容拐点

理论说"容量翻倍",CPython 的 list 真的翻倍吗?Python 没有 capacity() 接口,但可以用 sys.getsizeof 看对象占用的字节数——字节跳变的那一刻就是扩容拐点。下面把手写实现与内置写法并排对照。

示例 11-4 手写倍增与内置 list 并排对照:观察扩容拐点
# 手写倍增与内置 list 并排:打印扩容拐点(元素数 → 字节数)
import sys

class MyList:                       # 手写倍增动态数组
    def __init__(self):
        self._buf = [None] * 1
        self._size = 0
        self._cap = 1
    def push_back(self, x):
        if self._size == self._cap:     # 容量已满:倍增
            new_buf = [None] * (self._cap * 2)
            for i in range(self._size):
                new_buf[i] = self._buf[i]
            self._buf = new_buf
            self._cap *= 2
            print(f"{self._size}→{self._cap}", end="  ")  # 打印拐点
        self._buf[self._size] = x
        self._size += 1

print("手写倍增:", end=" ")
v = MyList()
for i in range(200):
    v.push_back(i)

print("\n内置 list:", end=" ")
a, last = [], sys.getsizeof([])
for i in range(1, 201):
    a.append(i)
    cur = sys.getsizeof(a)
    if cur != last:                 # 内存变化 = 一次扩容拐点
        print(f"{len(a)}→{cur}B", end="  ")
        last = cur
print()

扩容写错(如每次 +1)代价是 O(n2),且只有运行慢时才发现倍增由 CPython 保证,摊还 O(1);手写类也要照抄倍增骨架
free 忘记调用即泄漏引用计数 + 垃圾回收自动释放,无手动 free

11.6.2 实测数据解读

本机实测(CPython 3.11):list 连续 append 200 个元素,拐点(元素数 → 字节)序列 1→88B, 5→120B, 9→184B, 17→248B, 25→312B, 33→376B, 41→472B, 53→568B, 65→664B, 77→792B, 93→920B, 109→1080B, 129→1240B, 149→1432B, 173→1656B。换算容量(指针槽数)为 4, 8, 16, 24, 32, 40, 52, 64, 76, 92, 108, 128, 148, 172, 200——每次扩容约增加当前容量的 1/8,即约 1.125 倍。虽是 1.125 倍而非 2 倍,几何增长 ⇒ 摊还 O(1) 不变;总指针搬运 ≈ 9n,摊到每次仍是常数。不同 CPython 版本增长因子略异,摊还结论相同。

C 的手写扩容代码Python 的 list 接口
realloc 每次扩容都是裸内存搬运,策略(倍增还是 +1)写死在调用点append 自动倍增;策略由 CPython 决定,sys.getsizeof 把拐点暴露成可观测量

工程建议:Python 里管理扩容的四个招式
  • 预分配:知道要装多少时用 a = [None] * n 再按下标赋值,把扩容次数降为 0——摊还分析告诉你"扩容不贵",但一次都别扩更便宜;
  • 别写 a = a + [x]:每次把整个列表复制一遍,是"每次 +1"的平方级灾难;追加用 a.append(x),批量用 a.extend(it);
  • 遍历时别增删:for 循环里 a.remove/a.append 会让迭代错位;先收集再统一改,或用列表推导;
  • 增长因子不是越大越好:CPython 约 1.125 倍,比 2 倍更省内存;只要因子 > 1,摊还就仍是 O(1)。
误区 4:扩容增量太小,摊还证明失效

"每次 +1"的扩容不是常数因子增长:第 i 次扩容拷贝 i−1 个元素,总拷贝 Σi=1n i ≈ n2/2,摊还 O(n)——插入 10 万元素就要拷约 50 亿次。Python 里最常见的"每次 +1"写法就是 a = a + [x]:每次复制整表,长度 10 万时总复制 ≈ 50 亿次,肉眼可见地卡顿。list.append 的扩容因子约 1.125,是几何增长;"每次多开固定格数"的扩容是平方级灾难。

自测题

1. 摊还分析与平均情形分析的根本区别是什么?
参考答案

平均情形分析对输入的分布取平均(如"快排平均 O(n log n)"假设排列等可能),分布一变结论即失效;摊还分析对操作序列取平均,不假设任何概率——"n 次 list.append 总代价 O(n)"对任何序列都成立。

2. 为什么说"全 multiPop 的序列"不存在?这对证明意味着什么?
参考答案

multiPop 要弹出元素,而元素必须先 push 进去;从空栈开始的序列里,弹出总次数 ≤ 入栈总次数 ≤ n,multiPop 的总代价被 push 次数封顶——昂贵操作在结构上不可能频繁出现,总代价 ≤ 2n 对任何序列成立。

3. 动态数组扩容"存 1 元"为什么不够?给出会破产的序列。
参考答案

存 1 元 = 每次插入收费 2(1 元自用 + 1 元存款)。设 size = s、容量 c = 2k,总收费 2s,总花费 s + (c − 1),余额 = s − c + 1。数组一满(s = c)时余额只剩 1;此时扩容收 2 元、付 1 元自用、再付 c 元拷贝,余额 = 1 + 2 − 1 − c = 2 − c < 0——c ≥ 4 即破产。而"存 2 元"(收 3 元)时余额 = 2s − c + 1,利用 s ≥ c/2 得余额 ≥ 1 恒正。扩容是一次性大额开销,存款必须按"每个元素都积累足够配额"定价,2 元是最低安全价。

4. buildHeap 为什么是 O(n) 而不是 O(n log n)?差在哪一步?
参考答案

逐个 insert 到空堆是 O(n log n):每个元素要从底部上滤 log n 层;buildHeap 整体下滤时,多数结点在底层、下滤路径短:高度 h 的结点只有 n/2h+1 个,每个下滤 ≤ h 层,总代价 (n/2)·Σ h/2h = O(n)。差在"按高度计数"而非"按深度计数",同一棵树的两种视角。

5. 为什么 C++ 的 vector 扩容后迭代器全部失效,而 Python 的 list 扩容后已取出的引用仍然有效?这与摊还分析有何联系?
参考答案

vector 扩容要整体搬家到新内存,旧地址上的一切指针/迭代器随之作废;CPython 的 list 底层是对象指针数组,扩容只是把指针搬运到新数组,你手中的引用指向堆上的对象本身,与数组搬家无关——但遍历 list 时插入/删除会按索引错位,是另一副面孔。两者共通的是摊还 O(1) 的"倍增拷贝":vector 总拷贝 ≈ 2n,CPython 总指针搬运 ≈ 9n,都是常数摊还,由数学保证。

import sys

# ---------- 任务 1:带真实拷贝计数器的倍增动态数组 ----------
class DoublingArray:
    """倍增扩容:容量满时 ×2,记录每次 push_back 的真实拷贝次数。"""
    def __init__(self):
        self._buf = [None] * 1        # 底层存储,初始容量 1
        self._size = 0                # 元素个数
        self._cap = 1                 # 容量
        self.total_copies = 0         # 累计拷贝次数(真实代价总和)
        self.last_cost = 0            # 最近一次 push 付出的拷贝次数
        self.max_cost = 0             # 单次 push 的最大拷贝次数

    def push_back(self, x):
        self.last_cost = 0
        if self._size == self._cap:   # 容量已满:倍增扩容
            new_buf = [None] * (self._cap * 2)
            for i in range(self._size):
                new_buf[i] = self._buf[i]     # 真实拷贝 1 次
            self.last_cost = self._size       # 本次操作的真实拷贝代价
            self.total_copies += self._size
            if self.last_cost > self.max_cost:
                self.max_cost = self.last_cost
            self._buf = new_buf
            self._cap *= 2
        self._buf[self._size] = x
        self._size += 1

# ---------- 任务 1:每次只多 1 格的"笨扩容"(对照策略) ----------
class LinearArray:
    """每次容量只 +1:摊还代价退化为 O(n),用于对照。"""
    def __init__(self):
        self._buf = [None] * 1
        self._size = 0
        self._cap = 1
        self.total_copies = 0
        self.last_cost = 0
        self.max_cost = 0

    def push_back(self, x):
        self.last_cost = 0
        if self._size == self._cap:   # 容量已满:只多开 1 格
            new_buf = [None] * (self._cap + 1)
            for i in range(self._size):
                new_buf[i] = self._buf[i]
            self.last_cost = self._size
            self.total_copies += self._size
            if self.last_cost > self.max_cost:
                self.max_cost = self.last_cost
            self._buf = new_buf
            self._cap += 1
        self._buf[self._size] = x
        self._size += 1

# ---------- 任务 4:会计方法视角的"存 3 元"动态数组 ----------
# 每次 push 收 3 元:1 元支付"写入自己",2 元存入账户;
# 扩容时每拷贝 1 个旧元素,从账户支付 1 元。
# 证明(设 size = s,容量 = c = 2^k):
#   总收费 = 3s;总花费 = s + (1+2+...+c/2) = s + c - 1;
#   余额 = 3s - s - (c-1) = 2s - c + 1 ≥ 1 > 0。
# 所以"存 3 元"永远够用——摊还 O(1) 的会计证明。
class BankArray:
    def __init__(self):
        self._buf = [None] * 1
        self._size = 0
        self._cap = 1
        self.balance = 0              # 账户余额
        self.min_balance = float("inf")   # 全程最低余额(应恒 ≥ 0)

    def push_back(self, x):
        self.balance += 3             # 收 3 元
        self.balance -= 1             # 支付本次写入
        if self._size == self._cap:   # 扩容:每拷 1 个元素付 1 元
            new_buf = [None] * (self._cap * 2)
            for i in range(self._size):
                new_buf[i] = self._buf[i]
                self.balance -= 1
            self._buf = new_buf
            self._cap *= 2
        self._buf[self._size] = x
        self._size += 1
        if self.balance < self.min_balance:
            self.min_balance = self.balance

    # ---- 任务 4:会计方法验证"存 3 元"够不够 ----
    b = BankArray()

设计说明:① 三个类共用"满则扩容、循环拷贝"的骨架,差异只在扩容因子(×2 与 +1),暴露摊还分析的唯一变量;② 拷贝计数放在真实 for 循环而非切片/浅拷贝,统计语义代价而非底层内存搬运;③ 任务 4 用可运行的"余额"把抽象证明变成可观察的量,实测最低余额 2 与理论下界 1 吻合;④ 任务 5 用 sys.getsizeof 观察内存字节推断扩容拐点——CPython 没有 capacity() 接口,字节数是唯一可观测的"容量计",实测 1.125 倍增长与 §11.3 的"常数因子"证明互相印证。
